## 上下文

当前 `xgit annotate` 的核心链路仍然是“基于变更源直接取 diff hunk，然后把模板渲染结果插到目标文件里”。这个模型对首次运行足够简单，但它隐含了一个前提：目标文件里不存在上一次 annotate 生成、且仍属于当前待提交改动的注释块。

一旦实际工作流变成“先 annotate 一次，再继续补代码、删代码、改代码，最后再 annotate 一次”，这个前提就不成立了。已有注释块本身会出现在当前 diff 里，现有实现又不区分“业务代码新增”和“上一次 annotate 生成的注释外壳”，于是容易出现：

- `add` 注释块内部继续补代码后，再次运行时外面再套一个 `add`
- 原本属于同一个逻辑改动的内容被拆成多个零散 `add`/`modify`
- 已有注释块中的上下文信息无法复用，用户每次都要重新输入

另一方面，用户明确要求这个能力只能作用于“当前同一次提交的待处理改动”。如果某个注释块已经存在于基线版本中，它就是历史代码的一部分；在它上面的新改动必须生成新的注释，而不是去回滚、吞并或改写历史注释。

## 目标 / 非目标

**目标：**

- 让 `annotate` 在再次运行时能够识别当前待提交注释块，并在渲染前把它们还原为未注释的逻辑改动视图。
- 让系统基于“基线内容 vs 还原后的逻辑内容”重新计算净改动，再生成收敛后的最终注释结构。
- 让 `add`、`modify`、`del` 注释块在同一批待提交改动上支持多轮迭代，而不是随着多次 annotate 发生无意义嵌套。
- 在可安全判定时，从已有待提交注释块中提取运行时上下文，并提示用户是否复用。
- 为模板差异、旧代码渲染策略、历史注释块、多上下文并存、人工破坏注释块等情况建立保守而稳定的处理规则。

**非目标：**

- 不在本次变更中重写 setup、模板编辑模型或新增配置字段。
- 不要求系统必须从任意自定义模板中完整恢复所有上下文字段；无法可靠推断的字段允许回退到重新输入。
- 不在本次变更中自动合并跨文件、跨语义块的改动，只要求生成结果相对同一逻辑改动收敛。
- 不把历史已提交注释块升级为可回滚对象；历史注释块仍然是普通代码背景。

## 决策

### 决策 1：将 annotate 流程改为“识别 -> 还原 -> 重算 diff -> 重建注释”的两阶段模型

新的处理模型不再直接对当前变更源的原始 diff hunk 渲染注释，而是引入一个中间的“逻辑文件视图”：

1. 读取基线内容
   - staged 模式：基线为 `HEAD:path`
   - latest-commit 模式：基线为 `HEAD^:path`
2. 读取当前渲染内容
   - staged 模式：当前内容为 index/worktree 中待写回的版本
   - latest-commit 模式：当前内容为 `HEAD:path`
3. 在当前渲染内容中识别候选注释块，并判断哪些属于“当前待提交注释块”
4. 对这些待提交注释块执行还原，得到“逻辑文件视图”
5. 重新计算“基线内容 vs 逻辑文件视图”的净 diff
6. 再按现有 `add/modify/del` 模板生成最终注释块并写回

这样做的原因：

- 用户真正关心的是“当前净改动”应该怎样被注释，而不是“当前文件里所有新增行”都再包一层。
- 把“还原”和“重建”分开后，`add` 内继续新增、`modify` 内继续修改、`del` 内继续整理等场景都会自然收敛到新的净 diff 结果。
- 这个模型在 staged 和 latest-commit 两种变更源下都成立，只是基线快照不同。

备选方案：

- 在原始 diff 上做局部过滤，只跳过看起来像注释的新增行：实现较快，但无法解决“注释块内部又发生新改动”的归并问题。
- 简单地在再次运行时拒绝处理已有注释文件：安全，但会让工具失去多轮迭代能力。

### 决策 2：用“模板识别 + 基线增量判定”区分当前待提交注释块和历史注释块

候选注释块识别分成两步：

1. **结构识别**
   - 基于当前生效的 `block_templates.add/modify/del` 构造可逆匹配规则，识别起始行和结束行
   - 结合当前 `annotate.old_code` 显式策略、legacy `{old}` 语义和兼容 `// old:` 回退，识别哪些行属于旧代码记录、哪些行属于真实代码体
2. **待提交判定**
   - 只把“注释外壳行相对于基线快照是新增”的块视为当前待提交注释块
   - 已存在于基线中的注释块自动归类为历史注释块，不参与回滚

这样做的原因：

- 仅靠“长得像注释模板”无法区分历史注释和本轮注释；必须结合当前变更源相对基线的新增关系判断。
- 历史注释块在基线中已经存在，因此天然不满足“注释外壳是新增”这个条件。
- 这个判定规则直接对应用户提出的“只针对同一次 commit 改动生效”。

备选方案：

- 在源码注释里新增专用元数据标记：识别会更稳，但会把实现细节永久暴露到最终提交的源码中。
- 依赖外部状态文件记录上一次 annotate 结果：可以避免源码反解析，但跨进程/跨机器/手动编辑后的状态一致性较差。

### 决策 3：还原规则只恢复“逻辑代码体”，不依赖完整反解析旧代码

待提交注释块的还原规则按 kind 处理：

- `add`：移除注释外壳，保留代码体
- `modify`：移除注释外壳和旧代码记录，只保留代码体
- `del`：整个块从逻辑文件视图中移除

关键点是：还原阶段只需要恢复“当前净代码内容”，而不是先完整恢复一个带旧代码的历史状态。之后重新计算基线 diff 时，删除行和修改前旧行会自然从基线快照中重新得到。

这样做的原因：

- 对 `modify/del` 来说，旧代码真正可靠的来源是基线快照，而不是注释中的展示文本。
- 这让还原流程对 `old_code` 展示策略更加稳健；即使模板里不再完整保留旧代码文本，只要能识别出注释外壳与代码体，仍然能重建净 diff。
- 只有在判断块边界和代码体范围时需要识别旧代码展示区域，而不要求它成为重建的唯一数据源。

备选方案：

- 先完整从注释块里恢复 `old_lines/new_lines` 再直接组装新的 `HunkSegment`：理论上更直接，但对各种旧代码渲染风格和手工修改更脆弱。

### 决策 4：上下文复用仅作为“安全预填”，且只在唯一一致时触发

系统需要尽量从当前待提交注释块中提取：

- `reason`
- `reference_kind`
- `reference_value`

提取方式使用当前起始模板的反向匹配能力：用户模板里存在对应占位符时尝试恢复该字段，不存在或匹配失败时视为未知。

复用策略：

- 只有当所有可识别待提交注释块给出的某个字段值唯一一致时，才把它作为候选默认值
- 当候选默认值存在时，系统提示用户是否复用
- 当多个待提交块的上下文不一致，或字段无法可靠提取时，系统不得静默猜测，直接回退到常规输入流程
- `author_tag` 与 `date` 不参与复用，继续按本次运行的运行时上下文生成

这样做的原因：

- 用户要的是“减少重复输入”，不是让系统替用户冒险猜错上下文。
- 模板是可配置的，不是所有项目都会把全部字段都渲染到起始模板里，因此复用必须允许部分字段缺失。

备选方案：

- 只要发现已有注释就自动复用第一块的上下文：最省事，但在多上下文并存时风险过高。
- 完全不做复用：更简单，但无法满足用户明确提出的交互诉求。

### 决策 5：无法可靠还原时保守失败，不允许静默产生双重包裹

以下情况视为“无法安全重建”：

- 起始模板匹配到了，但找不到对应结束模板
- 同一区域存在重叠/交叉的待提交注释块
- 旧代码展示区域与代码体边界无法判定
- 反向识别结果和基线增量信息明显冲突

遇到这些情况时，系统必须对当前文件保守失败并给出明确提示，而不是跳过识别继续按原始 diff 渲染。因为后者最容易重新产生嵌套注释，反而放大文件损坏风险。

这样做的原因：

- 这项能力的核心价值是“比现在更稳”，而不是“尽量猜着继续跑”。
- 人工编辑坏的注释块、极端自定义模板和半成品状态都需要有清晰的安全边界。

## 风险 / 权衡

- [反向识别依赖当前模板，模板越自由，解析越脆弱] → 通过把“还原只依赖边界和代码体”作为主路径、把上下文字段恢复降级为尽力而为来降低风险。
- [同一文件中可能同时存在历史注释块和当前待提交注释块] → 通过“是否相对基线新增”做硬判定，避免误回滚历史注释。
- [保守失败会让部分极端场景不能自动完成 annotate] → 通过输出清晰错误并覆盖边界测试，优先保证不会产生更糟的嵌套结果。
- [两阶段 diff 计算会提升实现复杂度和测试矩阵] → 通过把识别、还原、净 diff 计算拆成独立模块，并用状态回放测试覆盖多轮 annotate 行为。

## Migration Plan

1. 在 `annotate` 流程中引入“基线内容 / 当前渲染内容 / 逻辑文件视图”的中间模型。
2. 为当前模板与旧代码展示策略实现候选注释块识别器，并加入“基线新增”判定。
3. 实现还原逻辑，把待提交注释块转换为逻辑文件视图。
4. 基于逻辑文件视图重新计算净 diff，并复用现有渲染器生成最终注释。
5. 增加上下文复用提示，并在无法安全还原时输出明确错误。
6. 为 staged / latest-commit、add / modify / del、历史块混入、模板差异、人工破坏等场景补充状态回放测试。

回滚策略：

- 如果识别器在实现阶段发现对某些模板配置不够稳定，可以先保留 staged/latest-commit 的基线模型和失败兜底，只对默认模板及兼容模板开放重建能力，并对不支持模板直接报安全错误。

## Open Questions

- 第一阶段是否需要支持“跨空白行自动合并相邻待提交块”，还是只要求通过净 diff 自然收敛。当前设计倾向于后者，避免语义猜测过多。
- 当一个文件内存在多个不同上下文的待提交块时，交互上是逐字段提示、逐块提示，还是直接放弃复用并要求重新输入。本次设计先定义为“不自动复用”，具体交互文案实现时细化。
