## 上下文

当前 setup 中有两类“开关 + 关联配置值”的条目：

- `annotate.block_templates.{add,modify,del}`：模板对象同时包含 `enabled`、`start`、`end`；
- `annotate.old_code`：旧代码处理既有“是否启用”的总开关，又有 `mode`、`line_comment.*`、`block_comment.*` 这些子配置。

`menuconfig-setup-navigation` 之后，这些条目都以“开关 + 子菜单”的方式呈现，但 setup 的切换逻辑并没有把“启用状态”和“配置值”分开对待：

- 模板开关关闭时直接执行 `*template = default_block_template(...)`，导致用户自定义的 `start` / `end` 被覆盖为默认模板；
- `旧代码处理` 开关关闭时把 `mode` 写成 `Some(None)`，重新开启时再写回 `None`（legacy），导致此前选中的 `line_comment` / `block_comment` 模式丢失。

这说明当前实现把“开关是否生效”和“下次恢复时应该使用什么值”混成了同一个状态源。模板分支的问题只发生在 setup UI 内；旧代码处理则已经触及配置模型本身，因为现有结构没有稳定的位置保存“禁用前最后一次有效模式”。

## 目标 / 非目标

**目标：**

- 让 setup 中带有关联配置值的开关项遵循统一语义：关闭只改变生效状态，不改变用户已配置的值。
- 修正 `新增格式`、`修改格式`、`删除格式` 的开关往返行为，保证模板文本在关闭和重新开启后保持不变。
- 修正 `旧代码处理` 的开关往返行为，保证其在关闭后重新开启时恢复到关闭前最后一次有效模式。
- 为现有开关项补充回归测试，防止未来再引入同类“关掉即抹值”的回归。

**非目标：**

- 不重做整个 setup 导航结构，也不调整菜单布局。
- 不改变 annotate 渲染本身的旧代码展示语义；这次只修复 setup/配置持久化层面对值保持的约束。
- 不把所有布尔开关都改造成带子菜单的数据结构；仅处理当前已有的关联值型开关。

## 决策

### 决策 1：把“关闭”定义为只停用当前能力，而不是重建默认配置

对于 setup 中任何“开关 + 子配置”的条目，关闭操作都必须只改变“当前是否启用”的状态，不得顺带把关联字段恢复为默认值、空字符串或其他兼容回退值。这样才能让开关状态和值状态在行为上彻底解耦。

备选方案：

- 继续允许每个开关自行决定关闭时是否重建默认值。缺点是语义会继续分散，用户无法预测某个开关是“暂时停用”还是“重置配置”。
- 在帮助文案里声明“关闭会恢复默认值”。缺点是这仍然把 destructive 行为绑定到一个普通开关上，不符合 menuconfig 场景下的直觉。

### 决策 2：模板开关沿用现有数据结构，仅修正 toggle 行为

`BlockTemplate` 已经天然区分了 `enabled` 与 `start/end`，因此模板问题不需要新的配置字段。实现上只需要把关闭模板的行为从“重置整个模板对象”改为“仅设置 `enabled = false`”，重新开启时也只改 `enabled = true`，保留既有 `start/end`。

备选方案：

- 在关闭模板时把当前值缓存到 setup 的临时状态中，再把配置对象重置为默认值。缺点是保存到磁盘时仍会丢值，而且让内存态和持久态分叉。
- 额外引入 `saved_start` / `saved_end` 字段。缺点是现有模型已经足够表达需求，引入镜像字段只会增加复杂度。

### 决策 3：为旧代码处理显式建模 `enabled`，停止复用 `mode=none` 表达禁用状态

`annotate.old_code.mode` 目前同时承担“采用何种展示模式”和“是否整体禁用”两层含义，导致禁用后无法保留此前的模式选择。为满足“关闭后再打开仍恢复原模式”的需求，需要把启用状态单独建模，例如在 `AnnotateOldCodeConfig` 中新增显式 `enabled` 标志，并让 `mode` 只表示启用状态下的模式选择：

- `enabled = false`：旧代码处理当前禁用，但 `mode` 保留最后一次有效值；
- `enabled = true` + `mode = None`：启用 legacy 旧代码语义；
- `enabled = true` + `mode = Some(LineComment|BlockComment)`：启用显式结构化模式。

加载兼容层继续接受历史配置中的 `mode = "none"`，并将其解释为 `enabled = false`；保存时应写出新的显式字段，避免再次丢失“禁用前的模式”。

备选方案：

- 继续沿用 `mode = Some(None)` 作为禁用哨兵，并在 setup 状态里额外缓存上次模式。缺点是只对当前会话有效，保存后再打开仍然丢失模式。
- 关闭旧代码处理时强制回到某个固定默认模式（例如 legacy）。缺点是本质上仍然是值串扰，只是把目标值从“当前值”换成了“默认值”。

### 决策 4：为现有关联值型开关建立回归矩阵，而不是只修单一分支

这次已确认的问题点集中在模板开关和旧代码处理开关，但根因是“toggle 行为没有统一约束”。因此测试应覆盖：

- `add` / `modify` / `del` 模板：编辑模板 -> 关闭 -> 重新开启 -> 值保持不变；
- `旧代码处理`：选择 `line_comment` 或 `block_comment` -> 关闭 -> 保存/重新载入（如实现涉及持久化）-> 重新开启 -> 模式保持不变；
- 其他现有 toggle 项：确认没有额外的值覆盖分支，至少通过 smoke test 固化现状。

备选方案：

- 只给 `modify` 或 `del` 单独补一个回归测试。缺点是无法防止 `add` 或旧代码处理在后续重构里再次走回老路。

## 风险 / 权衡

- [旧代码配置模型变更会影响加载/保存兼容层] → 通过兼容读取历史 `mode = "none"`，并在测试中覆盖旧配置加载路径来降低风险。
- [新版本保存的配置可能不再被旧版本二进制完整理解] → 明确把“保留禁用前模式”优先级置于旧版本回写兼容之上，同时在设计中把这一点记录为可接受权衡。
- [实现只修内存态、不修持久态导致问题仍在重启后复现] → 在任务中明确要求覆盖保存后重载场景，而不只验证同一会话内的 toggle 往返。

## 迁移计划

1. 先在配置层为旧代码处理引入可区分的启用状态，并补齐历史配置兼容读取逻辑。
2. 再调整 setup toggle 行为，让模板和旧代码处理都改为“只切换状态，不覆盖值”。
3. 最后补充 setup / config 回归测试，覆盖关闭、保存、重载、重新开启等完整往返路径。

回滚方式：

- 如果配置模型拆分带来不可接受的兼容问题，可先保留模板开关值保持修复，回滚旧代码处理的模型调整；两者在实现上可以拆分回退。
