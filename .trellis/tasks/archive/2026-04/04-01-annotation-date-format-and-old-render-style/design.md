## 上下文

当前注释规范化链路已经具备块级模板、自定义起止边界和 setup 配置入口，但仍有两个明显短板：

- `{date}` 在运行时由 `xgit/src/annotate.rs` 中的时间戳逻辑直接生成，导致默认输出不符合团队常见的日期规范。
- `modify` / `del` 的旧代码记录仍停留在“模板里包含 `{old}`”或“渲染器发现模板没写 `{old}` 就硬编码补 `// old:`”这两种隐式路径里，缺少结构化配置模型。

之前的归档设计已经明确把 old-code 表达模型重构留到后续处理，因此当前能力虽然足够兼容历史行为，但已经不足以满足“可格式化日期 + 可配置旧代码展示风格”的团队级要求。

## 目标 / 非目标

**目标：**

- 让 `{date}` 支持通过独立配置进行格式化，并默认输出 `yyyy-mm-dd`。
- 让旧代码记录拥有独立于 `block_templates` 的结构化渲染策略。
- 让显式旧代码策略能够覆盖 legacy `{old}` 占位符和兼容回退逻辑，避免重复输出。
- 让 `xgit setup` 可以直接编辑日期格式和旧代码展示策略，而不是迫使用户继续通过模板间接表达。
- 为未迁移项目保留兼容路径，避免一次性破坏现有工作流。

**非目标：**

- 不在本次变更中重写 diff hunk 划分、缩进对齐或空白行包裹策略。
- 不在本次变更中设计任意语法的模板 DSL，尤其不把旧代码逐行渲染完全外包给模板字符串。
- 不在本次变更中引入日期时区配置；`{date}` 只要求基于系统本地时间渲染。
- 不要求第一阶段的 setup 提供复杂的多行编辑器或模板校验器。

## 决策

### 决策 1：日期格式使用独立配置，而不是继续输出时间戳或把格式语法塞进模板

新增独立的日期配置，例如：

```toml
[annotate.date]
format = "yyyy-mm-dd"
```

`{date}` 继续作为模板占位符存在，但其实际值由“系统本地时间 + 有效配置中的日期格式”共同决定，而不是继续在运行时直接写入 Unix 时间戳。

选择这个方案的原因：

- 日期格式属于运行时上下文规则，而不是边界模板本身的语义；把它独立出来更符合用户认知。
- 用户明确提出团队要求是 `yyyy-mm-dd`，默认值应该直接对齐团队规范，而不是要求每个项目先手工迁移。
- 独立日期配置比在模板里引入 `{date:...}` 一类内联 DSL 更容易在 setup 中表达和解释。

备选方案：

- 继续保持时间戳输出：不满足用户需求，也无法体现“日期格式化能力”。
- 使用模板内联格式语法：灵活，但会把模板系统推向更复杂的占位符 DSL，超出本次范围。

### 决策 2：旧代码记录引入结构化渲染策略，而不是继续依赖 `{old}` 字符串拼接

新增独立的旧代码渲染配置，例如：

```toml
[annotate.old_code]
mode = "line_comment"

[annotate.old_code.line_comment]
layout = "per_line" # per_line | header_body
header = "old:"
body_prefix = "old: "
body_suffix = ""

[annotate.old_code.block_comment]
title = "cover old codes"
body_prefix = ""
```

其中：

- `none`：不展示旧代码
- `line_comment`：由渲染器负责生成注释语法，并支持“每行都带前缀”与“首行标题 + 内容行”两种布局
- `block_comment`：由渲染器负责生成块注释边界，并支持首行标题

选择这个方案的原因：

- 用户要求的三种风格本质上是“旧代码展示策略”，不是 block 边界模板的自然延伸。
- 继续沿用 `{old}` 只会得到带字面量 `\n` 的字符串替换，很难通用地表达“每行都 old:”或“用块注释包裹”的需求。
- 结构化策略可以让 setup 直接暴露“模式 + 模式参数”，比要求用户修改模板更稳妥。

备选方案：

- 继续依赖 `{old}`：无法优雅支持逐行前缀和块注释。
- 把旧代码完全交给模板：灵活，但会把本次变更扩大成整套多行模板 DSL 设计。

### 决策 3：显式旧代码策略优先，未配置时保留兼容语义

旧代码渲染优先级调整为：

1. 如果配置中显式定义了 `annotate.old_code.mode`，渲染器必须按显式策略输出旧代码。
2. 如果未显式定义旧代码策略，则保持当前兼容语义：
   - 起始模板包含 `{old}` 时，继续按 legacy 方式展开 `{old}`。
   - 起始模板不包含 `{old}` 时，继续按当前 header/body 的兼容回退补 `old:` 注释。

这意味着一旦用户显式选择了 `none`、`line_comment` 或 `block_comment`，系统就不再额外展开 `{old}` 或附加兼容回退，避免重复输出旧代码。

选择这个方案的原因：

- 显式配置必须可预期，不能再被旧模板语义“偷偷叠加”。
- 未迁移项目又必须保留历史行为，避免因为新增字段破坏已有规范化流程。

备选方案：

- 显式策略与 `{old}` 同时生效：会导致重复输出旧代码，行为不可预期。
- 引入单独的 `legacy_inline` 用户配置模式：能表达兼容态，但会把 setup 暴露成四种风格，增加理解成本。

### 决策 4：setup 使用“主模式 + 条件字段”暴露旧代码策略

`xgit setup` 在注释策略栏目中新增：

- 日期格式字段
- 旧代码展示模式字段
- 与旧代码模式对应的条件字段

例如：

- `mode = none` 时，不显示旧代码附加字段
- `mode = line_comment` 时，显示 `layout`、`header`、`body_prefix`、`body_suffix`
- `mode = block_comment` 时，显示 `title`、`body_prefix`

同时保留现有的 `add` / `modify` / `del` 起始模板与结束模板字段；用户不应被迫通过这些模板字段继续手写旧代码展示语法。

选择这个方案的原因：

- 日期格式和旧代码策略是新的独立概念，继续塞进 6 个模板字段里会让 setup 更难理解。
- 条件字段模型与当前 TUI 的单页字段展示方式兼容，比新增多级子页面更容易落地。

备选方案：

- 把旧代码策略完全藏在模板中：不满足“方便配置”的目标。
- 为旧代码策略再开一个二级页面：结构更完整，但对当前 setup 状态机改动更大。

### 决策 5：日期格式化使用独立实现/依赖，而不是手工拼接年/月/日

为了支持稳定的本地日期格式化，本次设计允许引入一个轻量日期时间依赖或等价辅助模块来处理：

- 系统本地时间获取
- 日期格式模板解析
- 格式化输出

优先考虑轻量、维护活跃、可在本地时区稳定工作的方案，而不是手工拼接字符串。

选择这个方案的原因：

- 当前需求虽然只强调 `yyyy-mm-dd`，但“支持日期格式化能力”意味着后续很可能还会出现更多格式诉求。
- 使用成熟日期时间能力比手写 `SystemTime -> 年/月/日` 转换更稳妥，也更容易测试。

备选方案：

- 手工把时间戳转换成 `yyyy-mm-dd`：初期可行，但扩展性和可维护性都较差。

## 风险 / 权衡

- [默认 `{date}` 从时间戳切换为格式化日期是可见行为变化] → 通过在提案与发布说明中明确默认变更，并允许项目配置覆盖格式来缓解。
- [显式旧代码策略与 legacy `{old}` 共存会增加优先级复杂度] → 通过固定“显式策略优先、未配置才兼容”的规则，并用回归测试覆盖。
- [setup 的条件字段会增加交互状态复杂度] → 通过把字段变化限制在注释策略单页内，并保持模式切换后的值落盘规则清晰可预测。
- [日期格式语法如果过于自由，后续校验和文档成本会升高] → 通过先定义有限、稳定的格式能力和默认值，避免一次性引入通用 DSL。

## Migration Plan

1. 在配置模型和默认配置中新增 `annotate.date` 与 `annotate.old_code` 结构，并定义默认日期格式。
2. 在注释运行时上下文中，用格式化日期替代当前时间戳输出。
3. 在渲染器中新增显式旧代码策略，并实现“显式策略优先、未配置时兼容”的优先级逻辑。
4. 扩展 `xgit setup` 的注释策略栏目，增加日期格式和旧代码模式相关字段。
5. 为默认配置、旧配置兼容、setup 落盘以及 `modify` / `del` 渲染结果补充回归测试。

回滚策略：

- 如果显式旧代码策略实现阶段发现兼容性问题，可以保留新增配置结构和规范定义，但临时让 setup 不写入显式模式值，以避免影响未迁移项目。
- 如果日期格式化实现出现依赖或平台问题，可以先收敛到固定的 `yyyy-mm-dd` 输出，再扩展为更通用的格式能力。

## Open Questions

- setup 打开未显式配置 `annotate.old_code` 的旧项目时，是否需要把兼容态显示为只读的“legacy”模式，还是直接映射到最近似的显式模式供用户编辑。本次设计倾向于保留兼容态提示，但实现阶段还需要结合当前 TUI 交互细化。
