# annotation-normalization 规范

## 目的
待定 - 由归档变更 xgit-setup-i18n-and-annotation 创建。归档后请更新目的。
## 需求
### 需求:注释规范化必须支持多种变更源
`xgit` 的注释规范化命令必须支持 `--staged` 和 `--latest-commit` 两种变更源，并默认使用 `--staged`。

#### 场景:默认使用 staged 变更
- **当** 用户运行注释规范化命令而未显式指定变更源
- **那么** 系统必须处理当前已 staged 的变更内容

#### 场景:处理最后一个提交
- **当** 用户运行注释规范化命令并指定 `--latest-commit`
- **那么** 系统必须基于最后一个提交相对其父提交的变更内容生成规范化结果

### 需求:staged 模式必须支持可配置的 untracked 文件纳入
在 staged 模式下，系统必须允许通过配置或命令参数决定是否把 untracked 文件作为新增文件候选一并处理。

#### 场景:启用 include untracked
- **当** staged 模式的有效配置启用了 `include_untracked`
- **那么** 系统必须把当前未跟踪文件视为新增文件候选并纳入注释规范化流程

### 需求:运行时上下文必须按策略表单采集
注释规范化命令必须根据有效策略配置，在每次执行时采集本次变更的上下文信息，而不是把这些动态值固定保存在长期配置中。

#### 场景:按引用类型采集本次上下文
- **当** 当前策略要求采集 `reason` 和引用类型/引用值
- **那么** 系统必须在执行时提示用户选择引用类型并填写本次变更的实际值

### 需求:系统必须按改动类型生成规范化注释
系统必须识别 `add`、`modify` 和 `del` 三类改动，并按有效策略模板生成对应的规范化注释块。

#### 场景:为修改代码生成 modify 注释
- **当** 某个变更块同时包含删除旧代码和新增新代码
- **那么** 系统必须按 `modify` 模板生成注释，并包含旧代码内容的记录

### 需求:注释规范化必须把结果写回目标文件
`xgit annotate` 完成后，必须把规范化注释真正写入目标文件内容；不得只在终端输出预览并报告成功。

#### 场景:staged 模式写回并更新已暂存结果
- **当** 用户在默认 `--staged` 模式下运行注释规范化命令
- **那么** 系统必须把生成后的注释块写回目标文件内容
- **并且** 命令完成后，`git diff --cached` 必须能够看到规范化后的已暂存结果

#### 场景:latest-commit 模式物化 amend 候选结果
- **当** 用户运行注释规范化命令并指定 `--latest-commit`
- **那么** 系统必须把规范化结果物化到工作区或索引中，供用户后续自行检查与 amend
- **并且** 系统不得只输出预览文本后直接报告处理完成

### 需求:注释渲染必须使用有效策略模板与身份字段
系统必须使用有效配置中的块级起始/结束模板、`identity.*` 与运行时表单字段渲染最终注释块；当新的块级模板未配置时，系统必须按兼容策略回退到旧 `annotate.policies.*`，不能退化为固定的硬编码占位格式。

#### 场景:使用项目级起始/结束模板覆盖默认模板
- **当** 项目配置覆盖了 `modify` 注释块的起始模板、结束模板与 `identity.author_tag`
- **那么** 渲染结果必须展开项目配置中的作者标识、日期、`reason`、引用类型和值
- **并且** 该 `modify` 注释块的起始行和结束行都必须符合项目配置中的模板，而不是固定的 `// end modify` 或调试样式

### 需求:注释必须围绕实际改动块插入
系统必须以 diff hunk 为单位插入注释，保证注释块使用有效配置中的起始模板和结束模板包裹实际新增、修改或删除的代码片段，而不是只生成文件级摘要或硬编码结尾文本。

#### 场景:新增代码块被自定义 add 模板包裹
- **当** 某个 C-like 源文件存在 staged 的新增代码块，并且有效配置把 add 结束模板设为 `//@}`
- **那么** 渲染后的文件内容必须在该新增代码块前插入配置的 add 起始模板
- **并且** 系统必须在该新增代码块后插入精确匹配 `//@}` 的结束模板，而不是 `// end add`

#### 场景:修改代码块记录 old 代码并包裹新代码
- **当** 某个变更块同时包含旧代码删除与新代码新增
- **那么** 渲染后的文件内容必须在该变更块附近插入有效配置中的 `modify` 起始模板和结束模板
- **并且** 该注释块必须按有效的旧代码展示策略包含对应的 `old` 代码记录

### 需求:系统必须支持文件规则到渲染器的映射
系统必须允许通过配置或 setup 维护的代码文件类型选择将文件类型映射到不同的注释渲染器，并在渲染器未实现时明确提示或跳过。

#### 场景:处理已启用的行注释语言文件
- **当** 目标文件命中了当前已启用的内置代码文件类型，并且该类型使用行注释块渲染器
- **那么** 系统必须使用行注释块渲染器生成 `add`、`modify` 或 `del` 注释

#### 场景:命中未实现的特殊渲染器
- **当** 目标文件命中了某个尚未实现的渲染器类型
- **那么** 系统必须明确提示该文件当前未被自动处理，而不是静默忽略

### 需求:系统必须匹配补齐后的内置代码文件扩展名
当用户启用了内置代码文件类型目录中的条目后，注释规范化流程必须能够让这些扩展名命中对应的文件规则，并进入现有的 `c_line_block` 渲染链路，而不是误判为“未匹配到文件规则”。

#### 场景:启用 C/C++ 分类后识别 hpp 文件
- **当** 用户启用了 `C/C++` 分类，并且 `networkmgr/routemgr/include/proxy_messsage_handler.hpp` 这类 `*.hpp` 文件出现在本次 annotate 处理范围内
- **那么** 系统必须将该文件命中到 `C/C++` 的内置文件规则
- **并且** 系统不得再输出“未匹配到文件规则”的跳过提示

#### 场景:启用 JavaScript 或 Kotlin 分类后识别脚本变体
- **当** 用户分别启用了 `JavaScript` 或 `Kotlin` 分类，并且待处理文件是 `*.mjs`、`*.cjs`、`*.jsx` 或 `*.kts`
- **那么** 系统必须把这些文件映射到现有的 `c_line_block` 渲染器
- **并且** 这些文件必须参与与同分类其他代码文件一致的注释规范化流程

### 需求:系统必须继续将非代码文件排除在内置默认匹配之外
系统必须保持内置默认代码文件规则的代码文件边界，禁止因为扩展代码文件目录而把非代码文件默认纳入自动注释范围。

#### 场景:默认内置规则仍然不会自动识别 Android.bp
- **当** 用户仅使用系统内置的默认代码文件类型目录与默认 `annotate.file_rules`
- **那么** 像 `Android.bp` 这样的非代码文件仍然不得被内置默认规则自动识别为可注释代码文件
- **并且** 系统只有在用户显式添加自定义规则时才可以处理这类文件

### 需求:latest-commit 模式不得隐式改写历史
在第一阶段，`--latest-commit` 模式必须只准备规范化后的结果，不得自动执行 amend 或其他历史改写操作。

#### 场景:latest-commit 处理完成
- **当** 系统完成 `--latest-commit` 模式的规范化
- **那么** 系统必须提示用户后续需要自行执行 amend 或其他确认步骤

### 需求:注释渲染必须支持缩进对齐策略
系统必须允许通过有效配置决定注释是否跟随被包裹代码的缩进对齐；当该策略启用时，注释起止行必须与对应代码块的有效缩进保持一致，而不是固定顶格输出。

#### 场景:启用缩进对齐后渲染新增代码块
- **当** 有效配置启用了注释缩进对齐，并且某个新增代码块本身带有前导缩进
- **那么** 系统必须让该代码块前后的注释行使用与该代码块一致的有效缩进

### 需求:注释渲染必须支持空白行包裹策略
系统必须允许通过有效配置决定注释块是否包裹变更中的空白行；当关闭空白行包裹时，注释块必须只围绕有效代码部分建立包裹边界，而不得因为空白行扩大包裹范围。

#### 场景:关闭空白行包裹后保留外围空白行
- **当** 有效配置关闭了空白行包裹，并且某个新增代码块前后包含空白行
- **那么** 系统必须保留这些空白行在文件中的原始位置
- **并且** 注释块必须只包裹该变更中的有效代码部分

### 需求:系统必须兼容旧版单段注释策略配置
系统必须允许现有仅配置 `annotate.policies.add/modify/del` 的项目在未显式迁移到新的块级模板配置时继续生成可用注释块，禁止因为缺少新字段而直接拒绝执行注释规范化。

#### 场景:仅存在旧版 add 策略配置
- **当** 有效配置中未定义 `annotate.block_templates.add.start` 和 `annotate.block_templates.add.end`，但定义了旧版 `annotate.policies.add`
- **那么** 系统必须继续使用旧版 add 策略作为新增代码块的起始模板来源
- **并且** 系统必须为对应的结束模板应用兼容默认值，而不是因为缺少新字段导致执行失败

### 需求:系统必须按可配置格式渲染注释日期
系统必须将 `{date}` 占位符渲染为基于系统本地时间的格式化日期文本，并允许通过有效配置指定日期格式；默认格式必须为 `yyyy-mm-dd`，不得继续默认输出 Unix 时间戳。

#### 场景:使用默认日期格式渲染注释
- **当** 有效配置未显式覆盖日期格式，并且系统在本地日期 `2026-04-01` 运行注释规范化
- **那么** 渲染后的 `{date}` 必须输出 `2026-04-01`
- **并且** 输出不得是 `1775029145` 一类 Unix 时间戳

### 需求:系统必须支持显式的旧代码展示策略
系统必须允许通过有效配置为 `modify` 和 `del` 注释块声明旧代码展示策略，并在显式策略存在时优先使用该策略，而不是继续依赖 `{old}` 占位符或硬编码兼容分支。

#### 场景:关闭旧代码展示
- **当** 有效配置将旧代码展示策略设为 `none`
- **那么** `modify` 或 `del` 注释块中必须不包含旧代码记录
- **并且** 系统不得因为模板中包含 `{old}` 或旧兼容逻辑再次输出旧代码

#### 场景:按行注释逐行展示旧代码
- **当** 有效配置将旧代码展示策略设为 `line_comment`，布局设为 `per_line`，且内容前缀设为 `old: `
- **那么** 变更块中的每一行旧代码都必须以对应渲染器的行注释语法输出
- **并且** 每一行旧代码前都必须附加 `old: ` 前缀

#### 场景:使用块注释展示旧代码
- **当** 有效配置将旧代码展示策略设为 `block_comment`，并把标题设为 `cover old codes`
- **那么** 系统必须使用对应渲染器的块注释边界包裹旧代码
- **并且** 旧代码块的首行必须包含 `cover old codes` 备注

#### 场景:未配置显式旧代码策略时保持兼容语义
- **当** 有效配置未定义显式旧代码展示策略，并且 `modify` 起始模板仍包含 `{old}`
- **那么** 系统必须继续按 legacy `{old}` 语义展开旧代码
- **并且** 系统不得额外附加新的结构化旧代码块

### 需求:系统必须在注释规范化前还原当前待提交注释块
当 `xgit annotate` 针对同一批尚未完成的提交改动再次运行时，系统必须先识别并还原当前待提交注释块，再基于还原后的逻辑代码状态重新计算净改动并生成注释，禁止直接对已有注释外壳再次包裹。

#### 场景:在 add 注释块内部继续新增代码后重新生成单一 add
- **当** 某个文件中的新增代码块已经在当前待提交改动中被生成为 `add` 注释块
- **并且** 开发者随后又在该 `add` 注释块包裹的代码体内部继续新增代码
- **那么** 系统再次运行注释规范化时必须先移除该当前待提交 `add` 注释块的外壳并恢复逻辑新增代码
- **并且** 系统最终必须只生成一个覆盖最新净新增结果的 `add` 注释块，而不是在原有 `add` 外再嵌套新的 `add`

#### 场景:再次运行但净代码未变化时保持幂等
- **当** 某个文件中的当前待提交注释块自上一次 annotate 后未发生任何净代码变化
- **那么** 系统再次运行注释规范化时必须保持该文件的注释结果稳定
- **并且** 系统不得因为重复执行而新增额外的注释边界、旧代码记录或嵌套块

### 需求:系统必须区分当前待提交注释块与历史注释块
系统必须根据当前变更源相对基线快照的差异，区分哪些注释块属于本轮待提交改动，哪些注释块已经存在于基线中；只有当前待提交注释块可以被还原和重建，历史注释块必须视为普通代码背景。

#### 场景:历史注释块上的新修改生成新的改动注释
- **当** 某个注释块已经存在于当前变更源的基线快照中
- **并且** 开发者本次只是在该历史注释块包裹的代码附近新增、修改或删除了业务代码
- **那么** 系统运行注释规范化时禁止回滚或吞并该历史注释块
- **并且** 系统必须把这次新改动视为新的 `add`、`modify` 或 `del` 候选并生成对应注释

#### 场景:latest-commit 模式只重建当前提交中的注释块
- **当** 用户在 `--latest-commit` 模式下运行注释规范化
- **那么** 系统判断当前待提交注释块时必须以 `HEAD^` 作为基线快照
- **并且** 只有相对于 `HEAD^` 新增的注释外壳才可以参与还原和重建

### 需求:系统必须安全复用已有运行时上下文
当系统能够从当前待提交注释块中可靠提取并验证一致的运行时上下文时，系统必须提示用户是否复用这些值作为本次 annotate 的默认输入；当上下文不唯一或无法可靠提取时，系统禁止静默猜测。

#### 场景:唯一一致上下文可作为默认值复用
- **当** 当前文件中的待提交注释块都能可靠提取出相同的 `reason`、`reference_kind` 和 `reference_value`
- **那么** 系统在本次注释规范化运行中必须提示用户是否复用这些值
- **并且** 用户确认复用后，系统必须将这些值作为当前运行的默认上下文输入

#### 场景:多上下文冲突时不得静默复用
- **当** 当前待提交注释块提取出的 `reason`、`reference_kind` 或 `reference_value` 存在冲突
- **那么** 系统不得自动选择其中任意一组值继续执行
- **并且** 系统必须回退到常规输入流程或显式要求用户重新确认

### 需求:系统必须在无法可靠还原时保守失败
当待提交注释块的结构、边界或上下文与当前模板规则不一致，导致系统无法可靠判定如何还原时，系统必须对该文件保守失败并给出明确提示，禁止在未完成还原的前提下继续对原始 diff 追加新的注释外壳。

#### 场景:待提交注释块边界损坏时中止该文件重建
- **当** 某个当前待提交注释块只能识别到起始边界而无法识别到合法结束边界
- **那么** 系统必须中止该文件的注释重建流程并提示注释块结构损坏
- **并且** 系统不得继续把该文件中的已有注释块当作普通新增代码再包裹新的注释

### 需求:系统必须显式汇总未格式化文件及原因
当 annotate 完成候选文件处理后，系统必须分别报告“已渲染文件”和“未格式化文件”的结果；当存在未格式化文件时，系统必须在结束阶段输出逐文件清单与原因，不得只保留模糊的总分母或依赖零散的中途跳过日志。

#### 场景:摘要区分已渲染与未格式化文件
- **当** annotate 处理了一批候选文件，其中只有部分文件成功进入渲染流程
- **那么** 系统必须在结束摘要中分别输出已渲染文件数量和未格式化文件数量
- **并且** 系统不得只输出会把未格式化文件混入分母的单一成功计数

#### 场景:不支持的文件类型进入未格式化清单
- **当** annotate 候选文件中包含 `networkmgr/routemgr/Android.bp`
- **并且** 该路径既未命中当前有效 `annotate.file_rules`，也不属于系统内置代码文件类型目录
- **那么** 系统必须在结束阶段把该文件列入未格式化清单
- **并且** 原因必须明确表示该类型当前不受支持

#### 场景:已知但未启用的内置后缀进入未格式化清单
- **当** annotate 候选文件中包含 `foo.cpp`
- **并且** `*.cpp` 属于系统内置代码文件类型目录
- **并且** 当前有效 `annotate.file_rules` 未启用 `*.cpp`
- **那么** 系统必须在结束阶段把该文件列入未格式化清单
- **并且** 原因必须明确表示当前设置未开启该后缀功能，而不是“不支持该类型”或“未匹配到文件规则”

#### 场景:命中未实现渲染器的文件进入未格式化清单
- **当** 某个候选文件命中了当前有效 `annotate.file_rules`
- **并且** 该规则对应的 renderer 尚未实现
- **那么** 系统必须在结束阶段把该文件列入未格式化清单
- **并且** 原因必须明确表示命中了尚未实现的渲染器

#### 场景:全部文件成功渲染时不输出未格式化清单
- **当** annotate 的所有候选文件都成功完成渲染
- **那么** 系统必须在结束摘要中把未格式化文件数量报告为 `0`
- **并且** 系统不得额外输出未格式化文件清单

### 需求:annotate 命令必须忽略仓库级 .xgit 目录
当 `xgit annotate` 处理候选文件或执行 `--latest-commit` 前置校验时，系统必须忽略当前 Git 工作区根目录下 `.xgit/` 及其子路径；但对于其他源码或普通未跟踪文件，系统仍必须维持原有的处理与阻塞行为。

#### 场景:默认 annotate 模式不得把 .xgit 纳入候选文件
- **当** 当前 Git 工作区根目录存在 `.xgit/` 及其内容
- **并且** 用户执行默认 `xgit annotate`
- **那么** 系统必须不把 `.xgit/` 下的任何文件纳入注释候选集合

#### 场景:仅存在仓库级 .xgit 配置目录时允许继续 latest-commit
- **当** 当前 Git 工作区中除仓库根目录 `.xgit/` 及其内容外不存在其他未提交改动
- **并且** 用户执行 `xgit annotate --latest-commit`
- **那么** 系统必须允许继续 latest-commit 模式的注释规范化流程

#### 场景:存在其他未跟踪文件时仍然拒绝 annotate latest-commit
- **当** 当前 Git 工作区中除了仓库根目录 `.xgit/` 外，还存在其他未跟踪或已修改文件
- **当** 用户执行 `xgit annotate --latest-commit`
- **那么** 系统必须拒绝执行
- **并且** 系统必须继续提示工作区当前不干净

#### 场景:忽略 .xgit 时仍继续使用仓库级配置
- **当** 当前项目的有效配置来自 `<git-root>/.xgit/config.toml`
- **并且** `.xgit/` 是 annotate 处理范围中唯一会被识别到的仓库级目录
- **当** 用户执行 `xgit annotate` 或 `xgit annotate --latest-commit`
- **那么** 系统必须继续按项目级配置参与本次 annotate 的有效配置合并
- **并且** 系统不得因为忽略 `.xgit/` 脏状态而回退到仅使用全局配置或默认配置
