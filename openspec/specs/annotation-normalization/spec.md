# annotation-normalization 规范

## 目的
待定 - 由归档变更 xgit-setup-i18n-and-annotation 创建。归档后请更新目的。
## 需求
### 需求:注释规范化必须支持多种变更源
`xgit` 的注释规范化命令必须支持 `--staged` 和 `--latest-commit` 两种变更源，并默认使用 `--staged`。

#### 场景:默认使用 staged 变更
- **当** 用户运行注释规范化命令而未显式指定变更源
- **那么** 系统必须处理当前已 staged 的变更内容

#### 场景:处理最后一个提交
- **当** 用户运行注释规范化命令并指定 `--latest-commit`
- **那么** 系统必须基于最后一个提交相对其父提交的变更内容生成规范化结果

### 需求:staged 模式必须支持可配置的 untracked 文件纳入
在 staged 模式下，系统必须允许通过配置或命令参数决定是否把 untracked 文件作为新增文件候选一并处理。

#### 场景:启用 include untracked
- **当** staged 模式的有效配置启用了 `include_untracked`
- **那么** 系统必须把当前未跟踪文件视为新增文件候选并纳入注释规范化流程

### 需求:运行时上下文必须按策略表单采集
注释规范化命令必须根据有效策略配置，在每次执行时采集本次变更的上下文信息，而不是把这些动态值固定保存在长期配置中。

#### 场景:按引用类型采集本次上下文
- **当** 当前策略要求采集 `reason` 和引用类型/引用值
- **那么** 系统必须在执行时提示用户选择引用类型并填写本次变更的实际值

### 需求:系统必须按改动类型生成规范化注释
系统必须识别 `add`、`modify` 和 `del` 三类改动，并按有效策略模板生成对应的规范化注释块。

#### 场景:为修改代码生成 modify 注释
- **当** 某个变更块同时包含删除旧代码和新增新代码
- **那么** 系统必须按 `modify` 模板生成注释，并包含旧代码内容的记录

### 需求:注释规范化必须把结果写回目标文件
`xgit annotate` 完成后，必须把规范化注释真正写入目标文件内容；不得只在终端输出预览并报告成功。

#### 场景:staged 模式写回并更新已暂存结果
- **当** 用户在默认 `--staged` 模式下运行注释规范化命令
- **那么** 系统必须把生成后的注释块写回目标文件内容
- **并且** 命令完成后，`git diff --cached` 必须能够看到规范化后的已暂存结果

#### 场景:latest-commit 模式物化 amend 候选结果
- **当** 用户运行注释规范化命令并指定 `--latest-commit`
- **那么** 系统必须把规范化结果物化到工作区或索引中，供用户后续自行检查与 amend
- **并且** 系统不得只输出预览文本后直接报告处理完成

### 需求:注释渲染必须使用有效策略模板与身份字段
系统必须使用有效配置中的块级起始/结束模板、`identity.*` 与运行时表单字段渲染最终注释块；当新的块级模板未配置时，系统必须按兼容策略回退到旧 `annotate.policies.*`，不能退化为固定的硬编码占位格式。

#### 场景:使用项目级起始/结束模板覆盖默认模板
- **当** 项目配置覆盖了 `modify` 注释块的起始模板、结束模板与 `identity.author_tag`
- **那么** 渲染结果必须展开项目配置中的作者标识、日期、`reason`、引用类型和值
- **并且** 该 `modify` 注释块的起始行和结束行都必须符合项目配置中的模板，而不是固定的 `// end modify` 或调试样式

### 需求:注释必须围绕实际改动块插入
系统必须以 diff hunk 为单位插入注释，保证注释块使用有效配置中的起始模板和结束模板包裹实际新增、修改或删除的代码片段，而不是只生成文件级摘要或硬编码结尾文本。

#### 场景:新增代码块被自定义 add 模板包裹
- **当** 某个 C-like 源文件存在 staged 的新增代码块，并且有效配置把 add 结束模板设为 `//@}`
- **那么** 渲染后的文件内容必须在该新增代码块前插入配置的 add 起始模板
- **并且** 系统必须在该新增代码块后插入精确匹配 `//@}` 的结束模板，而不是 `// end add`

#### 场景:修改代码块记录 old 代码并包裹新代码
- **当** 某个变更块同时包含旧代码删除与新代码新增
- **那么** 渲染后的文件内容必须在该变更块附近插入有效配置中的 `modify` 起始模板和结束模板
- **并且** 该注释块必须按有效的旧代码展示策略包含对应的 `old` 代码记录

### 需求:系统必须支持文件规则到渲染器的映射
系统必须允许通过配置或 setup 维护的代码文件类型选择将文件类型映射到不同的注释渲染器，并在渲染器未实现时明确提示或跳过。

#### 场景:处理已启用的行注释语言文件
- **当** 目标文件命中了当前已启用的内置代码文件类型，并且该类型使用行注释块渲染器
- **那么** 系统必须使用行注释块渲染器生成 `add`、`modify` 或 `del` 注释

#### 场景:命中未实现的特殊渲染器
- **当** 目标文件命中了某个尚未实现的渲染器类型
- **那么** 系统必须明确提示该文件当前未被自动处理，而不是静默忽略

### 需求:latest-commit 模式不得隐式改写历史
在第一阶段，`--latest-commit` 模式必须只准备规范化后的结果，不得自动执行 amend 或其他历史改写操作。

#### 场景:latest-commit 处理完成
- **当** 系统完成 `--latest-commit` 模式的规范化
- **那么** 系统必须提示用户后续需要自行执行 amend 或其他确认步骤

### 需求:注释渲染必须支持缩进对齐策略
系统必须允许通过有效配置决定注释是否跟随被包裹代码的缩进对齐；当该策略启用时，注释起止行必须与对应代码块的有效缩进保持一致，而不是固定顶格输出。

#### 场景:启用缩进对齐后渲染新增代码块
- **当** 有效配置启用了注释缩进对齐，并且某个新增代码块本身带有前导缩进
- **那么** 系统必须让该代码块前后的注释行使用与该代码块一致的有效缩进

### 需求:注释渲染必须支持空白行包裹策略
系统必须允许通过有效配置决定注释块是否包裹变更中的空白行；当关闭空白行包裹时，注释块必须只围绕有效代码部分建立包裹边界，而不得因为空白行扩大包裹范围。

#### 场景:关闭空白行包裹后保留外围空白行
- **当** 有效配置关闭了空白行包裹，并且某个新增代码块前后包含空白行
- **那么** 系统必须保留这些空白行在文件中的原始位置
- **并且** 注释块必须只包裹该变更中的有效代码部分

### 需求:系统必须兼容旧版单段注释策略配置
系统必须允许现有仅配置 `annotate.policies.add/modify/del` 的项目在未显式迁移到新的块级模板配置时继续生成可用注释块，禁止因为缺少新字段而直接拒绝执行注释规范化。

#### 场景:仅存在旧版 add 策略配置
- **当** 有效配置中未定义 `annotate.block_templates.add.start` 和 `annotate.block_templates.add.end`，但定义了旧版 `annotate.policies.add`
- **那么** 系统必须继续使用旧版 add 策略作为新增代码块的起始模板来源
- **并且** 系统必须为对应的结束模板应用兼容默认值，而不是因为缺少新字段导致执行失败

### 需求:系统必须按可配置格式渲染注释日期
系统必须将 `{date}` 占位符渲染为基于系统本地时间的格式化日期文本，并允许通过有效配置指定日期格式；默认格式必须为 `yyyy-mm-dd`，不得继续默认输出 Unix 时间戳。

#### 场景:使用默认日期格式渲染注释
- **当** 有效配置未显式覆盖日期格式，并且系统在本地日期 `2026-04-01` 运行注释规范化
- **那么** 渲染后的 `{date}` 必须输出 `2026-04-01`
- **并且** 输出不得是 `1775029145` 一类 Unix 时间戳

### 需求:系统必须支持显式的旧代码展示策略
系统必须允许通过有效配置为 `modify` 和 `del` 注释块声明旧代码展示策略，并在显式策略存在时优先使用该策略，而不是继续依赖 `{old}` 占位符或硬编码兼容分支。

#### 场景:关闭旧代码展示
- **当** 有效配置将旧代码展示策略设为 `none`
- **那么** `modify` 或 `del` 注释块中必须不包含旧代码记录
- **并且** 系统不得因为模板中包含 `{old}` 或旧兼容逻辑再次输出旧代码

#### 场景:按行注释逐行展示旧代码
- **当** 有效配置将旧代码展示策略设为 `line_comment`，布局设为 `per_line`，且内容前缀设为 `old: `
- **那么** 变更块中的每一行旧代码都必须以对应渲染器的行注释语法输出
- **并且** 每一行旧代码前都必须附加 `old: ` 前缀

#### 场景:使用块注释展示旧代码
- **当** 有效配置将旧代码展示策略设为 `block_comment`，并把标题设为 `cover old codes`
- **那么** 系统必须使用对应渲染器的块注释边界包裹旧代码
- **并且** 旧代码块的首行必须包含 `cover old codes` 备注

#### 场景:未配置显式旧代码策略时保持兼容语义
- **当** 有效配置未定义显式旧代码展示策略，并且 `modify` 起始模板仍包含 `{old}`
- **那么** 系统必须继续按 legacy `{old}` 语义展开旧代码
- **并且** 系统不得额外附加新的结构化旧代码块
