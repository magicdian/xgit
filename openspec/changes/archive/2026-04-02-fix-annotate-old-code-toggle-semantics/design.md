## 上下文

当前 annotate 的渲染结果同时受两组配置影响：一组是 `annotate.block_templates.{modify,del}.enabled` 这类“是否生成某类注释块”的模板开关；另一组是 `annotate.old_code.mode` 及其布局配置，这组配置决定旧代码如何展示。`menuconfig-setup-navigation` 把它们拆成了不同菜单，但运行时和帮助文案都没有把二者的边界固化下来，结果是：

- `modify` 模板已经关闭时，旧代码处理仍可能通过 legacy fallback 把 `old:` 注释带出来。
- 旧代码处理关闭时，`modify` 模板中的 `old={old}` 片段仍可能残留在输出中。
- `del` 模板是否真正可用依赖旧代码展示，但 setup 帮助栏没有说明这种前置关系。

这个问题同时影响 `xgit/src/annotate.rs` 的渲染路径和 `xgit/src/setup_ui.rs` / `resources/i18n/*.toml` 的帮助说明，因此需要一个跨模块设计来统一渲染矩阵与 UI 文案。

## 目标 / 非目标

**目标：**

- 让 `modify`、`del` 模板开关与旧代码处理开关的组合有稳定、可测试的运行时语义。
- 保证旧代码处理关闭时，`modify` 注释仍可独立工作，但不会残留 `old` 字段或旧代码正文。
- 保证 `del` 注释只在“删除模板开启 + 旧代码处理开启”时生效，并在 setup 帮助栏明确说明这一点。
- 让 setup 帮助内容与 annotate 真正执行的规则保持一致，避免 UI 说法与运行时行为相互矛盾。

**非目标：**

- 不重做 annotate 配置结构，也不引入新的顶层开关模型。
- 不改变 `add` 注释块的语义。
- 不在这次变更里重构整个 setup 帮助系统；仅补齐与这组开关联动直接相关的说明。

## 决策

### 决策 1：为 `modify` / `del` 渲染引入统一的前置条件判定

在 annotate 渲染入口增加集中判定逻辑，统一决定某类变更块是否允许渲染、是否允许附加旧代码、以及在不能渲染时应返回什么原因。这样可以把“模板开关”和“旧代码处理开关”的组合规则从分散的 if/else 中抽出来，避免 `modify`、`del` 和 legacy fallback 各自绕过约束。

备选方案：

- 在每个渲染分支里单独补判断。缺点是 `modify`、`del` 与旧代码 fallback 仍容易漂移。
- 仅依赖模板字符串是否包含 `{old}` 判断是否展示旧代码。缺点是无法表达“旧代码处理显式关闭应优先于模板文本”。

### 决策 2：`modify` 与 `del` 采用不同的禁用语义

`modify` 块同时拥有“新代码”与“旧代码”两个维度，因此当旧代码处理关闭而 `modify` 模板开启时，系统仍应生成 `modify` 注释，只是移除旧代码记录与 `old` 字段残留。`del` 块只承载被删除的旧代码，因此在旧代码处理关闭时，`del` 模板即使开启也不应继续渲染，而应进入未格式化结果并给出明确原因。

备选方案：

- 让 `modify` 和 `del` 都在旧代码处理关闭时直接整体跳过。缺点是会让“我只想保留修改注释外壳”的场景失效，不符合用户预期。
- 让 `del` 在旧代码处理关闭时输出空壳删除注释。缺点是删除块没有有效正文，最终只会制造无意义包裹。

### 决策 3：关闭旧代码处理时清理模板中的 `old` 残留，而不是要求用户手工改模板

无论 `modify.start` 或 `del.start` 是否遗留 `old={old}` 一类片段，只要运行时判定旧代码不可展示，最终输出都必须移除这类占位结果，而不是留下 `old=`、空字符串拼接痕迹，或者退回 legacy `old:` 注释。这样可以保持配置兼容性，避免要求用户先手改模板才能真正关闭旧代码输出。

备选方案：

- 配置迁移时直接改写模板文本。缺点是侵入性较强，也会让用户不容易理解是谁修改了自己的模板。
- 继续保留 legacy fallback。缺点是与“显式关闭旧代码处理”直接冲突。

### 决策 4：把依赖关系直接写进 setup 上下文帮助，而不是只写在 README 或状态栏

`修改格式`、`删除格式` 和 `旧代码处理` 的语义容易被误解，因此帮助栏需要直接描述当前项的生效条件和与其他项的关系。帮助栏就在用户切换开关的现场，能减少“界面已关闭但运行时仍生效”的认知落差。

备选方案：

- 只在 README 里补说明。缺点是 setup 内操作时仍然看不到。
- 只在命令失败或跳过时提示。缺点是问题出现得太晚，用户已经形成错误预期。

## 风险 / 权衡

- [兼容依赖 legacy `{old}` 展开的旧模板] → 显式关闭旧代码处理后，这类模板将不再输出内联旧代码；通过保留模板文本本身、只在运行时抑制展开来降低迁移成本。
- [删除块被更多地计入“未格式化”结果] → 在摘要和帮助栏中提供明确原因，避免用户把它误解为渲染器异常。
- [帮助文案与运行时规则再次漂移] → 通过围绕同一套开关矩阵补充测试，要求 setup 帮助文本覆盖关键依赖说明。

## 迁移计划

这次变更不引入新的配置文件字段，也不需要迁移现有 TOML 结构。

实施顺序：

1. 先收敛 annotate 的判定矩阵和旧代码占位清理逻辑，并补齐对应单元测试。
2. 再更新 setup 帮助文案与本地化资源，确保界面说明与最终行为一致。
3. 最后补充未格式化结果与帮助说明的回归测试，防止后续再次引入隐式 fallback。

回滚方式：

- 如果新矩阵导致回归，可整体回滚到旧的渲染判定逻辑与帮助文案，不涉及配置数据迁移或存储格式恢复。
