## 上下文

当前 `xgit/src/annotate.rs` 在遍历候选文件时，遇到未命中文件规则或命中未实现渲染器的情况，会立刻 `println!` 一条“跳过 …”日志；等整个命令结束后，再输出一次 `status.annotate.summary = "注释渲染完成：{count}/{total}"`。这个实现有两个问题：

1. 结束摘要的分母直接使用 `changes.len()`，把成功渲染和被跳过的文件混在一起，用户很难从摘要判断“到底还有哪些文件没被处理”。
2. `select_renderer()` 只告诉调用方“有没有命中有效 renderer”，但不会解释失败原因。当前 `None` 会一律落到“未匹配到文件规则”，导致“系统不支持该类型”和“系统已知但设置未开启”这两类场景无法区分。

这次需求同时涉及 annotate 核心执行流、内置代码文件类型目录和终端文案，因此适合先把运行时状态模型和原因判定规则设计清楚，再去落 spec 与实现。
另外，用户已经明确要求把本次发版目标同步提升到 `2604.1.4`，因此这次设计还需要把版本更新纳入迁移步骤，但仍然保持“Cargo 版本为唯一来源”的既有约束不变。

## 目标 / 非目标

**目标：**

- 让 annotate 在命令结束时明确输出“已渲染文件数”和“未格式化文件数”，不再让成功数被模糊的总分母稀释。
- 为每个未格式化文件提供稳定原因，至少覆盖：
  - 系统不支持该类型
  - 系统已知该后缀，但当前设置未开启
  - 命中了未实现渲染器
- 让 latest-commit 与 staged 两种模式共享同一套结果汇总逻辑，避免行为分叉。
- 让原因判定优先复用现有 `code_file_types` 内置目录，而不是在 annotate 内部重新维护一份文件类型知识。
- 把版本目标更新为 `2604.1.4`，并继续通过 `Cargo.toml` 作为唯一版本来源。

**非目标：**

- 不在本次变更中新增新的内置文件类型或新的 renderer。
- 不调整 setup 界面的选项结构，只消费它已经写入到 `annotate.file_rules` 的结果。
- 不改变 annotate 的 diff 归并、注释重建或运行时上下文字段采集逻辑。

## 决策

### 决策 1：引入“候选文件处理结果”模型，替代遍历过程中的即时打印

`annotate::run()` 将从“边遍历边打印”改为“先为每个候选文件得到一个结构化结果，再在命令尾部统一输出”。新的结果模型至少需要表达三类状态：

- `Rendered`: 文件成功进入现有渲染与写回链路
- `Unformatted`: 文件未被格式化，并携带可本地化的原因枚举
- `Failed`: 保留当前会直接 `bail!` 的硬失败语义，例如 staged 模式下存在 unstaged 冲突、规范化失败等

这样做有三个直接收益：

1. 结束摘要可以准确基于 `Rendered` / `Unformatted` 计数生成，而不是复用 `changes.len()`。
2. “未格式化文件清单”可以在命令末尾集中输出，顺序稳定，测试也更容易断言。
3. 原先零散的“跳过”分支会收敛成统一的结果构建逻辑，避免后续再新增原因时把文案散落在多个 `println!` 分支里。

**备选方案：**只保留即时 `println!`，并额外维护几个计数器。  
**不采用原因：** 这样虽然能修正摘要数字，但无法自然支持最终的“未格式化：<path> (<reason>)”清单，也会让测试继续依赖中间日志顺序。

### 决策 2：基于“内置目录是否认识该路径”区分未支持类型与设置未开启

当前 `code_file_types.rs` 已经维护了所有内置条目的 `pattern` 与 `renderer`，这份目录正好可以回答“系统是否已知这个后缀”。因此 annotate 侧不再自己硬编码扩展名集合，而是新增面向运行时判断的辅助能力，例如：

- 判断某个路径是否命中任一内置 `CodeFileTypeEntry`
- 如果命中，判断对应 entry 是否出现在当前有效 `annotate.file_rules` 中

分类规则按以下优先级执行：

1. 若 `select_renderer()` 命中 renderer 且 renderer 已实现，则正常渲染。
2. 若 `select_renderer()` 命中 renderer 但 renderer 未实现，则记为 `Unformatted(RendererUnimplemented(renderer))`。
3. 若 `select_renderer()` 未命中，但路径可命中内置条目，则记为 `Unformatted(BuiltinTypeDisabled)`，文案表现为“设置未开启该后缀功能”。
4. 若 `select_renderer()` 未命中，且路径也不属于任何内置条目，则记为 `Unformatted(UnsupportedType)`，文案表现为“不支持该类型”。

这让用户示例里的两类输出都能稳定成立：

- `Android.bp` → `未格式化：networkmgr/routemgr/Android.bp (不支持该类型)`
- `xxx.cpp` 在用户关闭 `*.cpp` 后 → `未格式化：xxx.cpp (设置未开启该后缀功能)`

**备选方案：**在 annotate 里根据扩展名字符串直接 `match` 判断。  
**不采用原因：** 会把文件类型知识复制第二份，后续扩充内置目录时容易漏改，且无法自然复用 setup 已有的条目定义。

### 决策 3：将摘要改为“已渲染 / 未格式化”双计数，并在摘要后输出清单

为了消除现有 `count/total` 的歧义，结束文案不再只输出单个分式，而是分别输出：

- 已渲染文件数
- 未格式化文件数

如果未格式化数量大于 0，则在摘要后逐行输出统一格式的清单：

- `未格式化：<path> (<reason>)`

`latest-commit` 模式的“请用户手动 amend”提示保持存在，但位置固定为摘要前，避免它插入在未格式化清单中间影响可读性。

**备选方案：**保留 `count/total`，仅在非 100% 时补充清单。  
**不采用原因：** 即使增加清单，`10/11` 依然会把“已渲染”和“候选总数”绑定在一起，用户仍然需要二次解释分母含义；双计数更直观，也更便于本地化。

### 决策 4：对自定义 passthrough 规则保持保守解释

`setup` 允许用户保留未知的 passthrough 规则。对这类规则，本次设计只在两种情况下做明确分类：

- 命中 passthrough 规则但 renderer 未实现 → `RendererUnimplemented`
- 完全没有命中任何规则，但路径命中内置目录 → `BuiltinTypeDisabled`

如果某个路径既未命中任何规则，也不属于内置目录，本次统一视为 `UnsupportedType`。也就是说，对于“用户本来打算自己配置 custom rule，但实际上没配上”的情况，系统不会额外猜测，只给出“当前不支持该类型”的保守结论。

**备选方案：**为自定义规则缺失再新增一类“未配置自定义规则”。  
**不采用原因：** annotate 无法可靠知道用户的主观意图；继续细分会让提示看似更聪明，实则容易误导。

## 风险 / 权衡

- [内置目录只覆盖系统已知类型，因此某些用户自定义语法文件仍会被归类为“不支持该类型”] → 通过在 design 和 spec 中明确这是保守行为，优先保证结论稳定且不猜用户意图。
- [输出模型从即时打印改为统一汇总，可能影响现有测试对终端顺序的断言] → 用结构化结果驱动新的摘要/清单测试，并只保留 latest-commit hint 的稳定输出位置。
- [未来若新增更多 renderer 或文件类型，原因枚举可能继续扩展] → 让“未格式化原因”在代码中成为显式枚举，而不是散落的字符串判断，降低后续扩展成本。

## Migration Plan

这是纯命令行行为调整，不涉及配置迁移或数据迁移。

上线步骤：

1. 在 annotate 运行时引入结构化结果与未格式化原因枚举。
2. 在 `code_file_types` 中补充面向路径判断的辅助函数，供 annotate 复用内置目录。
3. 更新中英文摘要和未格式化原因文案。
4. 补充 annotate 结果输出测试，覆盖内置禁用后缀、未知类型和未实现 renderer。
5. 将 `xgit/Cargo.toml` 的 `package.version` 与相关版本测试/文档同步更新为 `2604.1.4`。

若实现后发现某类原因判断不稳定，可以先保留结构化汇总与清单输出，只把可疑分类回退到更保守的“未匹配到文件规则/不支持该类型”，避免错误引导用户去修改 setup。
版本部分如果需要回滚，也只应回滚 `Cargo.toml package.version` 与对应测试期望值，不得引入新的版本常量绕过现有版本单一来源规范。
