## 新增需求

### 需求:系统必须在注释规范化前还原当前待提交注释块
当 `xgit annotate` 针对同一批尚未完成的提交改动再次运行时，系统必须先识别并还原当前待提交注释块，再基于还原后的逻辑代码状态重新计算净改动并生成注释，禁止直接对已有注释外壳再次包裹。

#### 场景:在 add 注释块内部继续新增代码后重新生成单一 add
- **当** 某个文件中的新增代码块已经在当前待提交改动中被生成为 `add` 注释块
- **并且** 开发者随后又在该 `add` 注释块包裹的代码体内部继续新增代码
- **那么** 系统再次运行注释规范化时必须先移除该当前待提交 `add` 注释块的外壳并恢复逻辑新增代码
- **并且** 系统最终必须只生成一个覆盖最新净新增结果的 `add` 注释块，而不是在原有 `add` 外再嵌套新的 `add`

#### 场景:再次运行但净代码未变化时保持幂等
- **当** 某个文件中的当前待提交注释块自上一次 annotate 后未发生任何净代码变化
- **那么** 系统再次运行注释规范化时必须保持该文件的注释结果稳定
- **并且** 系统不得因为重复执行而新增额外的注释边界、旧代码记录或嵌套块

### 需求:系统必须区分当前待提交注释块与历史注释块
系统必须根据当前变更源相对基线快照的差异，区分哪些注释块属于本轮待提交改动，哪些注释块已经存在于基线中；只有当前待提交注释块可以被还原和重建，历史注释块必须视为普通代码背景。

#### 场景:历史注释块上的新修改生成新的改动注释
- **当** 某个注释块已经存在于当前变更源的基线快照中
- **并且** 开发者本次只是在该历史注释块包裹的代码附近新增、修改或删除了业务代码
- **那么** 系统运行注释规范化时禁止回滚或吞并该历史注释块
- **并且** 系统必须把这次新改动视为新的 `add`、`modify` 或 `del` 候选并生成对应注释

#### 场景:latest-commit 模式只重建当前提交中的注释块
- **当** 用户在 `--latest-commit` 模式下运行注释规范化
- **那么** 系统判断当前待提交注释块时必须以 `HEAD^` 作为基线快照
- **并且** 只有相对于 `HEAD^` 新增的注释外壳才可以参与还原和重建

### 需求:系统必须安全复用已有运行时上下文
当系统能够从当前待提交注释块中可靠提取并验证一致的运行时上下文时，系统必须提示用户是否复用这些值作为本次 annotate 的默认输入；当上下文不唯一或无法可靠提取时，系统禁止静默猜测。

#### 场景:唯一一致上下文可作为默认值复用
- **当** 当前文件中的待提交注释块都能可靠提取出相同的 `reason`、`reference_kind` 和 `reference_value`
- **那么** 系统在本次注释规范化运行中必须提示用户是否复用这些值
- **并且** 用户确认复用后，系统必须将这些值作为当前运行的默认上下文输入

#### 场景:多上下文冲突时不得静默复用
- **当** 当前待提交注释块提取出的 `reason`、`reference_kind` 或 `reference_value` 存在冲突
- **那么** 系统不得自动选择其中任意一组值继续执行
- **并且** 系统必须回退到常规输入流程或显式要求用户重新确认

### 需求:系统必须在无法可靠还原时保守失败
当待提交注释块的结构、边界或上下文与当前模板规则不一致，导致系统无法可靠判定如何还原时，系统必须对该文件保守失败并给出明确提示，禁止在未完成还原的前提下继续对原始 diff 追加新的注释外壳。

#### 场景:待提交注释块边界损坏时中止该文件重建
- **当** 某个当前待提交注释块只能识别到起始边界而无法识别到合法结束边界
- **那么** 系统必须中止该文件的注释重建流程并提示注释块结构损坏
- **并且** 系统不得继续把该文件中的已有注释块当作普通新增代码再包裹新的注释
