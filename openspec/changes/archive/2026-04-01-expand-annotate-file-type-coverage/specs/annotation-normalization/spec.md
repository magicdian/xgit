## ADDED Requirements

### 需求:系统必须匹配补齐后的内置代码文件扩展名
当用户启用了内置代码文件类型目录中的条目后，注释规范化流程必须能够让这些扩展名命中对应的文件规则，并进入现有的 `c_line_block` 渲染链路，而不是误判为“未匹配到文件规则”。

#### 场景:启用 C/C++ 分类后识别 hpp 文件
- **当** 用户启用了 `C/C++` 分类，并且 `networkmgr/routemgr/include/proxy_messsage_handler.hpp` 这类 `*.hpp` 文件出现在本次 annotate 处理范围内
- **那么** 系统必须将该文件命中到 `C/C++` 的内置文件规则
- **并且** 系统不得再输出“未匹配到文件规则”的跳过提示

#### 场景:启用 JavaScript 或 Kotlin 分类后识别脚本变体
- **当** 用户分别启用了 `JavaScript` 或 `Kotlin` 分类，并且待处理文件是 `*.mjs`、`*.cjs`、`*.jsx` 或 `*.kts`
- **那么** 系统必须把这些文件映射到现有的 `c_line_block` 渲染器
- **并且** 这些文件必须参与与同分类其他代码文件一致的注释规范化流程

### 需求:系统必须继续将非代码文件排除在内置默认匹配之外
系统必须保持内置默认代码文件规则的代码文件边界，禁止因为扩展代码文件目录而把非代码文件默认纳入自动注释范围。

#### 场景:默认内置规则仍然不会自动识别 Android.bp
- **当** 用户仅使用系统内置的默认代码文件类型目录与默认 `annotate.file_rules`
- **那么** 像 `Android.bp` 这样的非代码文件仍然不得被内置默认规则自动识别为可注释代码文件
- **并且** 系统只有在用户显式添加自定义规则时才可以处理这类文件
