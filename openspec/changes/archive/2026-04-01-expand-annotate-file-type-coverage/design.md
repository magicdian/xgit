## 上下文

当前 `xgit` 的代码文件类型目录由 `xgit/src/code_file_types.rs` 维护，setup 通过这份内置目录把结构化选择映射回 `annotate.file_rules`。但这份目录目前只覆盖了 7 个条目：`C/C++` 的 `.c/.h/.cpp`，`Java` 的 `.java`，`JavaScript` 的 `.js`，`Rust` 的 `.rs`，以及 `Kotlin` 的 `.kt`；默认规则集甚至只写入了 `.c/.h/.cpp/.java`。这意味着只要代码库里使用了同一语言族下更常见的变体扩展名，`annotate` 就会把它们当成“未匹配到文件规则”的文件直接跳过。

用户已经明确了本次范围边界：只补齐代码文件，不把 `Android.bp` 这类构建/配置文件纳入内置识别目录。因此这次设计的重点不是引入新渲染器，而是在现有 `c_line_block` 渲染链路不变的前提下，把当前已接入语言族中的常见代码扩展名覆盖补完整，并同步更新 setup、默认配置、回写逻辑和版本号。

## 目标 / 非目标

**目标：**
- 补齐当前已接入语言分类中的常见代码扩展名，避免 `annotate` 错过同语法族的代码文件。
- 保持 setup 的五个现有语言分类和 `annotate.file_rules -> renderer` 执行模型不变。
- 明确区分代码文件与非代码文件，确保 `Android.bp` 这类样本继续维持未内置支持状态。
- 把版本目标更新为 `2604.1.3`，并继续通过 `Cargo.toml` 作为唯一版本来源。

**非目标：**
- 不引入新的注释渲染器或新的注释语法族。
- 不在本次变更中新增非代码文件、构建文件或固定文件名规则。
- 不重写 setup 的层级交互模型，也不改造配置格式为新的持久化结构。
- 不在本次变更中扩展到新的语言家族（例如新增独立的 TypeScript、AIDL 或 Proto 分类）。

## 决策

### 决策 1：坚持“代码文件优先”，显式排除非代码规则

本次内置目录只扩展代码文件扩展名，不新增 `Android.bp`、`Android.mk`、`.gradle` 等构建或配置规则。虽然这些文件也能使用 `//` 注释，但用户已经明确本次只关注代码文件；把非代码文件一并纳入会让默认行为变得模糊，也容易扩大自动改写范围。

备选方案：
- 一并纳入所有 `//` 风格文件：覆盖面更大，但会违背本次边界，并把构建脚本也纳入默认自动处理范围。
- 用单独开关控制“代码文件 / 配置文件”：方向可行，但超出本次需要解决的问题。

### 决策 2：在现有五个分类内补齐常见扩展名，而不是新增分类

保持 `C/C++`、`Java`、`JavaScript`、`Rust`、`Kotlin` 五个现有分类不变，只扩展这些分类内部的条目。首批补齐矩阵如下：

- `C/C++`: `.c`、`.h`、`.cpp`、`.cc`、`.cxx`、`.hpp`、`.hh`、`.hxx`、`.ipp`、`.inl`、`.tpp`
- `Java`: `.java`
- `JavaScript`: `.js`、`.mjs`、`.cjs`、`.jsx`
- `Rust`: `.rs`
- `Kotlin`: `.kt`、`.kts`

这样可以直接解决用户已经命中的 `*.hpp` 问题，同时把当前语言族下明显常见的代码文件变体补齐，而不需要同步修改 setup 的一级导航结构。

备选方案：
- 新增更多一级分类（例如 TypeScript）：长期可扩展，但会让本次变更从“补齐已接入格式”扩大成“引入新语言族”。
- 只补 `*.hpp`：能修复眼前问题，但仍会留下 `.cc/.cxx/.kts/.mjs` 等同类漏匹配问题。

### 决策 3：继续使用 `c_line_block` 作为统一渲染器映射

本次新增的内置扩展名全部继续映射到现有 `c_line_block` 渲染器，不新增新的 renderer id。当前这些代码文件都使用兼容的行注释语法，而且 `annotate` 的实现本质上依赖 diff 与模板渲染，不需要做语言级 AST 解析，因此继续复用现有 renderer 可以把风险收敛在规则目录与配置回写层。

备选方案：
- 为不同语言家族拆分独立 renderer：未来可能有价值，但本次没有新的注释语法诉求，会显著扩大改动面。
- 直接让 setup 保存“扩展名集合”而非 `file_rules`：模型更贴近 UI，但会破坏当前执行链路并增加迁移复杂度。

### 决策 4：默认选择策略沿用分类语义，不单独为新条目定制默认值

默认仍然选中 `C/C++` 和 `Java` 两个分类；由于默认值是按分类生成的，因此新增到 `C/C++` 分类中的条目（如 `.hpp/.cc/.cxx` 等）会自动成为默认启用项，而 `JavaScript` 和 `Kotlin` 分类下新增的 `.mjs/.cjs/.jsx/.kts` 仍然只有在用户启用对应分类后才参与匹配。

这样既能修复 C/C++ 代码库里最容易出现的“默认配置漏识别”，又不改变当前“默认不开启 JavaScript/Kotlin”这一行为边界。

备选方案：
- 所有新增条目默认关闭：会导致默认选中分类内部语义不一致，用户仍会在 C/C++ 中遇到漏匹配。
- 把 JavaScript/Kotlin 也改成默认选中：会改变现有默认处理范围，超出本次预期。

### 决策 5：版本更新仍然只修改 Cargo 版本来源

版本号继续只从 `xgit/Cargo.toml` 的 `package.version` 读取，并把本次目标更新为 `2604.1.3`。设计上不新增任何额外版本常量，也不在 OpenSpec 以外引入第二份版本配置。

备选方案：
- 额外维护一个发布版本常量：会重新引入多处版本源问题。
- 只更新文档不更新规范：无法保证后续 `--version`、README 和测试保持一致。

## 风险 / 权衡

- [默认 C/C++ 覆盖面扩大] → 可能让更多 C/C++ 辅助实现文件默认进入 annotate；缓解方式是只纳入明确属于代码文件的常见扩展名，并继续允许用户在 setup 中关闭整个分类或单个条目。
- [目录扩充后多处定义容易漂移] → `code_file_types.rs`、默认配置、i18n 文案和测试都要同步；缓解方式是让默认规则尽量由内置目录生成或围绕同一矩阵补齐测试，避免手工分叉。
- [模板/内联实现扩展名存在团队差异] → 如 `.ipp/.inl/.tpp` 并非每个团队都使用；缓解方式是它们归属于可关闭的 `C/C++` 子项，而不是强制单独暴露新分类。
- [JavaScript 生态边界仍有残留] → 本次只补 `.mjs/.cjs/.jsx`，不扩到 TypeScript；缓解方式是在设计中明确这是“现有分类补齐”，后续若需要再以新变更扩展语言家族。

## Migration Plan

1. 在 `code_file_types.rs` 中扩充五个现有分类的内置条目，并同步补齐中英文标签。
2. 更新默认 `annotate.file_rules` 与 setup 的选择/回写测试，确保结构化目录与扁平规则集双向一致。
3. 补充 annotate 侧回归测试，验证新增代码扩展名会命中 `c_line_block`，而 `Android.bp` 仍然不会被内置规则自动识别。
4. 将 `xgit/Cargo.toml` 的 `package.version` 更新为 `2604.1.3`，并同步更新 README / 版本测试中的期望值。

回滚策略：若新增扩展名引发误匹配，可以整体回退本变更；由于未引入新配置格式，回滚只需恢复内置目录、默认规则与版本值。
