## 新增需求

### 需求:系统必须兼容旧版单段注释策略配置
系统必须允许现有仅配置 `annotate.policies.add/modify/del` 的项目在未显式迁移到新的块级模板配置时继续生成可用注释块，禁止因为缺少新字段而直接拒绝执行注释规范化。

#### 场景:仅存在旧版 add 策略配置
- **当** 有效配置中未定义 `annotate.block_templates.add.start` 和 `annotate.block_templates.add.end`，但定义了旧版 `annotate.policies.add`
- **那么** 系统必须继续使用旧版 add 策略作为新增代码块的起始模板来源
- **并且** 系统必须为对应的结束模板应用兼容默认值，而不是因为缺少新字段导致执行失败

## 修改需求

### 需求:注释渲染必须使用有效策略模板与身份字段
系统必须使用有效配置中的块级起始/结束模板、`identity.*` 与运行时表单字段渲染最终注释块；当新的块级模板未配置时，系统必须按兼容策略回退到旧 `annotate.policies.*`，不能退化为固定的硬编码占位格式。

#### 场景:使用项目级起始/结束模板覆盖默认模板
- **当** 项目配置覆盖了 `modify` 注释块的起始模板、结束模板与 `identity.author_tag`
- **那么** 渲染结果必须展开项目配置中的作者标识、日期、`reason`、引用类型和值
- **并且** 该 `modify` 注释块的起始行和结束行都必须符合项目配置中的模板，而不是固定的 `// end modify` 或调试样式

### 需求:注释必须围绕实际改动块插入
系统必须以 diff hunk 为单位插入注释，保证注释块使用有效配置中的起始模板和结束模板包裹实际新增、修改或删除的代码片段，而不是只生成文件级摘要或硬编码结尾文本。

#### 场景:新增代码块被自定义 add 模板包裹
- **当** 某个 C-like 源文件存在 staged 的新增代码块，并且有效配置把 add 结束模板设为 `//@}`
- **那么** 渲染后的文件内容必须在该新增代码块前插入配置的 add 起始模板
- **并且** 系统必须在该新增代码块后插入精确匹配 `//@}` 的结束模板，而不是 `// end add`

#### 场景:修改代码块记录 old 代码并包裹新代码
- **当** 某个变更块同时包含旧代码删除与新代码新增
- **那么** 渲染后的文件内容必须在该变更块附近插入有效配置中的 `modify` 起始模板和结束模板
- **并且** 该注释块必须包含对应的 `old` 代码记录
