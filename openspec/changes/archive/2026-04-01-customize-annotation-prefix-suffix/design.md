## 上下文

当前注释规范化链路已经具备三块基础能力：

- `annotate.policies.add/modify/del` 用于定义注释模板文本。
- `c_line_block` 渲染器负责把模板包裹到实际 diff hunk 周围。
- `xgit setup` 提供注释策略、渲染开关和代码文件类型的交互式配置入口。

但现状仍有两个关键限制：

- 配置模型只有“单段模板”，没有独立的结束模板。
- `c_line_block` 对输出格式仍带有实现层硬编码：非空注释统一走 `// ` 前缀，结束行统一是 `// end add|modify|del`。

这意味着即使用户能改 `annotate.policies.*`，也仍然无法表达 `// add by xx ... {@` 与 `//@}` 这种团队常用的成对包裹格式。与此同时，`setup_ui.rs` 当前也只暴露了 `add/modify/del` 三个单字段策略，缺少结束模板的编辑入口。

## 目标 / 非目标

**目标：**

- 让 `add`、`modify`、`del` 三类注释块都支持独立的起始模板和结束模板。
- 让模板足以表达带完整注释语法的输出行，例如 `// ... {@` 和 `//@}`。
- 让 `xgit setup` 可以查看和编辑新的起止模板配置。
- 为已有仅配置 `annotate.policies.*` 的用户提供兼容和迁移路径。

**非目标：**

- 不在本次变更中重写 diff hunk 识别、缩进对齐或空白行包裹策略。
- 不在本次变更中引入新的非 `c_line_block` 渲染器能力模型。
- 不要求第一阶段在 setup 中提供复杂的多行模板编辑器；单值编辑能力即可满足当前需求。

## 决策

### 决策 1：新增块级模板配置，而不是继续扩展 `annotate.policies.*`

新增显式的块级模板模型，例如：

- `annotate.block_templates.add.start`
- `annotate.block_templates.add.end`
- `annotate.block_templates.modify.start`
- `annotate.block_templates.modify.end`
- `annotate.block_templates.del.start`
- `annotate.block_templates.del.end`

这些字段表示“最终注释边界行的模板”，允许直接包含注释语法本身，例如 `// add by {author_tag} {date} ... {@` 或 `//@}`。渲染时系统只负责变量展开和缩进对齐，不再额外自动补 `// `。

选择这个方案的原因：

- 仅增加“结束模板”字段但保留 `// ` 自动前缀，仍然无法表达 `//@}` 这类无空格后缀。
- 继续沿用 `annotate.policies.*` 再附加若干格式开关，会把“模板内容”和“注释语法样式”耦合成更多隐式规则，长期更难理解和维护。

备选方案：

- 在现有 `annotate.policies.*` 旁边新增 `annotate.policy_suffixes.*`：能解决硬编码结尾，但仍无法解决 `//@}` 这种注释前缀细节。
- 保持内容模板不变，增加 `comment_prefix` / `comment_suffix` 一类渲染参数：对简单样式可行，但对起始和结束格式不对称的团队规范支持不足。

### 决策 2：配置加载阶段对旧字段做归一化兼容

运行时以 `annotate.block_templates.*` 为统一模型，但配置加载器必须兼容旧 `annotate.policies.*`：

- 如果新字段存在，优先使用新字段。
- 如果新字段缺失但旧 `annotate.policies.<kind>` 存在，则把旧值归一化为 `<kind>.start`。
- 对归一化场景的 `<kind>.end` 使用兼容默认值（例如 `// end add`）。

这样做的原因：

- 旧用户升级后不应因为缺少新字段而失去注释能力。
- 运行时统一使用一个模型，能避免渲染器同时分支处理“新旧两套配置”。

备选方案：

- 要求用户手工迁移配置后才能继续使用：风险高，会直接破坏现有工作流。
- 在磁盘上自动改写老配置：侵入性较强，也会让一次普通执行带来额外文件变更。

### 决策 3：`c_line_block` 只负责模板展开、缩进和包裹位置，不再硬编码结束行

`c_line_block` 的职责调整为：

- 对 `start` / `end` 模板做变量展开。
- 按当前 `align_with_code_indent` 策略为模板每一行补齐前导缩进。
- 在计算好的变更窗口前后插入展开后的起止模板。

它不再：

- 为非空行统一添加 `// `。
- 自动生成 `end add|modify|del`。

`modify` / `del` 场景中旧代码的记录逻辑保持现有语义：若起始模板未显式包含 `{old}`，渲染器仍可继续插入兼容的 `old:` 注释信息，避免这次变更扩大到 old-code 表达模型重构。

备选方案：

- 让模板继续只表示内容文本，再经过 `c_line_comment()` 包装：无法满足用户给出的真实模板。
- 让模板完全接管 old-code 的多行格式：灵活，但会把本次变更扩大成整套块模板 DSL 设计。

### 决策 4：setup 使用“六个显式模板字段”暴露起止模板

在注释策略栏目中，把现有三个策略字段扩展为六个字段：

- `add start`
- `add end`
- `modify start`
- `modify end`
- `del start`
- `del end`

加载旧配置时，界面展示的是归一化后的运行时值；保存时优先写出新 `annotate.block_templates.*` 结构。

选择这个方案的原因：

- 对当前 TUI 架构最直接，用户也容易理解“每种改动各有起止模板”。
- 不需要额外引入嵌套表单或复杂编辑器即可满足单行模板场景。

备选方案：

- 把每种改动包装成二级子页面：结构更完整，但对当前 setup 状态机改动更大。
- 继续保留旧三字段并增加“结束模板总开关”：可见性不足，不利于用户理解。

## 风险 / 权衡

- [原始模板更灵活，也更容易写错] → 通过提供兼容当前行为的默认模板，并在 setup 文案中明确这些字段需要包含完整注释前缀来降低误用概率。
- [保存配置后会从旧字段形态切换到新字段形态] → 通过加载兼容和保存前可视化编辑，确保行为不变，只改变持久化结构。
- [渲染器不再自动补 `// ` 后，模板责任更重] → 通过把“完整边界行模板”作为明确契约写入规范，避免实现和用户两侧都误以为系统还会隐式加前缀。
- [兼容逻辑增加配置合并复杂度] → 通过在配置加载阶段一次性归一化，避免把兼容分支散落到渲染和 setup 代码里。

## Migration Plan

1. 为配置模型新增 `annotate.block_templates` 及其对应的默认值、反序列化和合并逻辑。
2. 在配置加载阶段加入“新字段优先、旧 `policies.*` 回退”的归一化流程。
3. 改造 `c_line_block` 渲染器，使其使用起始/结束模板直接输出注释边界行。
4. 更新 `xgit setup` 的注释策略字段定义和保存逻辑，使其可编辑六个模板字段。
5. 为默认配置、旧配置兼容、渲染结果和 setup 编辑流程补充测试。

回滚策略：

- 如果新模板模型在实现阶段暴露出兼容性问题，可以保留加载兼容逻辑并临时继续使用旧 `policies.*` 作为主渲染源，但不应回滚已经定义好的规范契约。

## Open Questions

- setup 在第一阶段是否需要对模板做基础校验（例如提示未包含注释前缀），还是先只做原样保存和渲染。本次设计倾向于先保证表达能力，校验可以后续追加。
