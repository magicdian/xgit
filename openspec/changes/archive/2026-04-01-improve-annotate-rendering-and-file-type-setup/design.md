## 上下文

`xgit` 已经具备交互式 setup、注释模板渲染和 `annotate.file_rules` 到渲染器的映射能力，但当前两处体验仍然偏底层实现导向：

- 注释块始终顶格渲染，无法和目标代码缩进保持一致。
- 注释块对空白行采用固定包裹策略，无法按团队偏好调整。
- setup 把代码文件类型暴露为 `pattern=renderer;...` 字符串，和现有 menuconfig 风格的层级导航不一致，也无法自然表达“分类全选 / 部分选中 / 未选中”的状态。

这次变更同时跨越 `annotate` 渲染逻辑、配置模型和 setup 交互状态机，适合先把用户可见行为和底层映射方式设计清楚，再进入实现。

## 目标 / 非目标

**目标：**

- 让注释渲染支持可配置的缩进对齐策略和空白行包裹策略。
- 让 setup 以结构化的“代码文件类型”选择替代原始文件规则字符串编辑。
- 为代码文件类型建立可扩展的语言分类模型，支持分类层级的全选、部分选中和未选中状态。
- 在不破坏现有 `annotate.file_rules` 执行链路的前提下，把 setup 的结构化选择映射回稳定的渲染器规则。

**非目标：**

- 不在本次设计中引入新的插件式渲染器 ABI。
- 不要求 setup 在第一阶段完整暴露任意自定义 renderer 的高级编辑界面。
- 不在本次变更中自动改变已有用户配置中的注释渲染默认行为；新增选项默认保持与当前行为兼容。

## 决策

### 决策 1：新增显式的注释渲染配置，而不是把行为隐藏在模板里

在 `annotate` 下新增一层渲染选项，建议模型如下：

- `annotate.render.align_with_code_indent: bool`
- `annotate.render.wrap_blank_lines: bool`

默认值保持与当前输出兼容：

- `align_with_code_indent = false`
- `wrap_blank_lines = true`

这样做的原因是这两个选项描述的是“注释块如何包裹代码”，属于渲染器行为，而不是模板文案本身。若继续把它们塞进 `annotate.policies.*` 模板，模板会承担不属于它的排版责任，也会让 setup 无法用开关方式表达行为差异。

备选方案：

- 直接改变默认渲染行为，不新增配置：实现更快，但会让未进入 setup 的现有用户在同样输入下得到不同结果。
- 通过模板特殊占位符驱动缩进/空行策略：可行，但模板复杂度和用户心智负担都更高。

### 决策 2：代码文件类型采用“结构化选择 UI + 扁平 file_rules 持久化”

setup 将不再直接编辑 `pattern=renderer;...` 字符串，而是维护一个内置的可选代码文件类型目录。目录包含：

- 分类：`C/C++`、`Java`、`JavaScript`、`Rust`、`Kotlin`
- 子项：
  - `C/C++` → `.c`、`.h`、`.cpp`
  - `Java` → `.java`
  - `JavaScript` → `.js`
  - `Rust` → `.rs`
  - `Kotlin` → `.kt`

默认选中：

- `C/C++`
- `Java`

底层仍然把选择结果写回 `annotate.file_rules`，并把以上内置类型全部映射到现有 `c_line_block` 渲染器。也就是说，UI 层负责“结构化表达”，执行层继续消费扁平 `file_rules`。

这样做的原因是：

- `annotate.rs` 当前已经围绕 `file_rules -> renderer` 工作，保留这个执行契约可以减少变更面。
- setup 可以在不重写注释执行模型的前提下得到更好的 menuconfig 体验。
- 未来要增加新语言时，只需要扩展内置目录和默认映射，不必重新设计持久化格式。

备选方案：

- 直接把配置格式改成分层的 `annotate.code_file_types`：更贴近 UI 结构，但会扩大配置迁移范围，也需要同步重写执行层。
- 继续保留原始字符串编辑：兼容性最好，但无法满足层级多选、部分选中和后续扩展诉求。

### 决策 3：分类层使用三态展示，叶子层使用二态选择

setup 在代码文件类型选择器中采用两级层级与三态汇总：

- 分类层：
  - `[x]` 分类下全部子项已选中
  - `[-]` 分类下部分子项已选中
  - `[ ]` 分类下全部子项未选中
- 叶子层：
  - `[x]` 当前扩展名已启用
  - `[ ]` 当前扩展名未启用

交互约定：

- 在分类层按 `Enter` 进入子项列表。
- 在分类层按 `Space` 时，对该分类执行“全选 / 全取消”切换。
- 在叶子层按 `Space` 时切换单个扩展名。
- 在子层按 `Enter` 或 `Esc` 返回上一层。

这和现有 setup 的“主菜单 -> 字段列表”层次一致，也符合 menuconfig 常见操作习惯。

备选方案：

- 只做一层多选扩展名列表：实现简单，但分类扩展后会迅速失去可读性。
- 分类层只允许进入子层，不支持 `Space` 批量切换：更保守，但会降低效率。

### 决策 4：空白行策略第一阶段定义为“是否允许空白行落在包裹范围内”

当 `wrap_blank_lines = true` 时，保持当前行为，注释块可以包裹变更块中的空白行。

当 `wrap_blank_lines = false` 时，渲染结果必须只围绕有效代码部分建立包裹边界；空白行不得被视为必须包裹的内容。第一阶段实现应优先保证：

- 变更块前后的空白行不会强制扩大包裹边界。
- 关闭该选项不会破坏 `modify` / `del` 对 `old` 内容的记录语义。

之所以这样定义，是因为“按有效代码段重新切分 hunk”会显著增加 `modify/delete` 场景的复杂度。设计上先把用户可感知的包裹策略建模清楚，再允许实现阶段以稳定方式落地这一行为。

备选方案：

- 只处理首尾空白行：风险更低，但会把行为定义得过窄。
- 把空白行关闭解释为“按非空 run 强制拆分多个注释块”：语义最彻底，但需要更复杂的 hunk 切分与测试矩阵。

### 决策 5：保留未知自定义 file_rules，避免 setup 成为破坏性编辑器

如果用户配置文件中存在不属于内置代码文件类型目录的 `annotate.file_rules` 条目，setup 在保存时必须保留这些未知规则，而不是直接覆盖掉。结构化选择器只管理内置目录可识别的规则集合。

这样做的原因是：

- setup 正在从“原始文本编辑”过渡到“结构化编辑”，不能因此隐式删掉高级用户的自定义规则。
- 这允许后续逐步把更多 renderer 类型纳入 UI，而不是一次性做完全部高级配置。

## 风险 / 权衡

- [状态机复杂度提升] setup 从“菜单 / 字段 / 文本编辑 / 退出确认”扩展到多层弹窗与子选择器 → 通过把交互模式整理为显式模态状态，而不是继续叠加布尔值，降低后续维护风险。
- [结构化 UI 与扁平配置之间存在映射成本] 代码文件类型目录和 `file_rules` 之间需要双向转换 → 通过内置目录元数据统一管理分类、扩展名、pattern 和 renderer，减少散落逻辑。
- [空白行策略的语义边界可能被误解] “不包裹空白行”容易被理解为简单裁边或按 run 拆块 → 通过规范场景明确用户可见结果，并在设计中声明第一阶段优先保证稳定映射与可测试性。
- [默认新增更多语言分类后，用户可能误以为都已启用] → 通过默认只勾选 `C/C++` 与 `Java`，并在分类层显示明确状态摘要，降低误解。

## Migration Plan

1. 为配置模型增加 `annotate.render.*` 字段，并在默认配置中写入兼容当前行为的默认值。
2. 引入内置代码文件类型目录，把 setup 当前的 `file_rules` 文本项迁移为结构化选择器摘要展示。
3. 在 setup 保存时，把结构化选择结果映射为规范化的 `annotate.file_rules`，同时保留未知自定义规则。
4. 调整 `annotate` 渲染逻辑，使其读取新的渲染选项并改变注释输出位置与包裹边界。
5. 为新增配置字段、结构化选择器、三态分类展示和渲染结果补充回归测试。

回滚策略：

- 若新的结构化选择器存在严重交互问题，可以临时回退到只读摘要 + 旧文本编辑方式，但渲染选项配置与注释渲染逻辑可以独立保留。

## Open Questions

- `C/C++` 分类在第一阶段是否只覆盖现有 `.c/.h/.cpp`，还是要同时纳入 `.cc/.hpp/.cxx` 等扩展名。当前设计按已讨论范围，仅要求前三种。
- setup 是否需要显式提示“存在 N 条自定义规则未在结构化选择器中展示”，还是只要求保存时保留未知规则。本次设计优先保证保留，不强制增加提示文案。
